# 面试宝典接口与页面对照审查

> 修订状态：下文保留1.0版审查快照。接口文档1.1.0已修复导出结构、参数约束及示例错误，并补齐R2～R5、R9要求的前端接入约定；这不代表原型页面已实现接入。当前结果见`api-design.md`的“审查问题修订记录”。

审查日期：2026-10-22。范围：`src/main.js`、`docs/api-design.json`、`docs/api-design.md`、`docs/openapi.json` 及三个文档生成/校验脚本。

## 结论

按页面聚合数据、一次保存整场面经、后台处理AI与题单、固定简历版本的总体方向合理。但是，当前版本不能直接作为已经完成页面核对的联调基线：存在响应模型导出错误、前端数据结构适配缺失、异步交互未闭环等问题。

本次发现 **3项P1和6项P2问题**，其中包含文档确定错误与前端接入阻塞，以下分别说明。P1表示会阻断主要展示或调用；P2表示特定操作或边界情况下会出错或造成联调歧义。

本报告是审查结果，接口契约与应用代码尚未按报告修改。当前没有后端或真实数据库，无法验证接口实际执行、鉴权、事务和性能。本次验证是源码与契约的静态对照。

## 一、问题清单

### R1 · P1 · OpenAPI导出丢失响应模型引用及必返约束

**类型：确定的导出错误。**

证据：`scripts/export-openapi.mjs:34` 的 `responseSchema` 先调用 `objectSchema(fields)`，再把得到的标准Schema交回自定义字段转换器。转换器只认识自定义的`ref`，不保留已经生成的`allOf`；标准Schema的`required`数组也被当成字段标记再次转换。

实际检查结果：全部18个JSON接口都有至少一个必返字段从最终`data.required`丢失。两个文件下载接口不使用JSON响应，不在此计数内。

例如首页导出的结构实际相当于：

```json
{
  "data": {
    "type": "object",
    "properties": {
      "user": { "description": "当前用户简要资料……" },
      "resumes": { "type": "array", "items": {} }
    }
  }
}
```

这里既没有`user`关联`UserSummary`，也没有简历数组元素关联`Resume`。Apifox/ApiPost导入后可能看到响应对象，但无法可靠展开字段、生成类型或按契约Mock数据。Schema没有写约束本身是合法的，因此通用格式校验不会报错。

**建议：** 自定义字段只转换一次；生成完业务`data`的标准Schema后，直接嵌入响应外层。增加对最终`openapi.json`的检查：模型引用可追踪、`data.required`完整、数组元素不是空Schema、嵌套对象必返字段不丢失。当前`verify-api-docs.mjs:47`主要检查自定义源模型和示例，没有覆盖导出后的响应约束。

### R2 · P1 · 页面变量与接口字段不匹配，不能直接赋值

**类型：前端接入阻塞；不意味着后端必须沿用原型字段名。**

证据：`src/main.js:12`及首页、简历、题库、面经模板（第14、15、18、19行）。页面目前使用下面的字段，接口使用另一套字段：

| 页面字段 | 接口字段 | 接入时的转换规则 |
| --- | --- | --- |
| `r.type` | `file_type` | 文件格式映射；DOC/DOCX都可以使用文档图标 |
| `r.active` | `is_active` | 同步选中标记，切换后只能有一个选中项 |
| `r.date` | `updated_at` | UTC时间转换成“刚刚”“2天前”等页面文本 |
| `r.parsed` | `parse_status` | 不能只转成真假；等待、解析中、成功、失败应分别展示 |
| `q.type` | `category` | technical→技术问题，hr→人资问题，unclassified→待分类 |
| `q.level`中文文本 | `level`英文枚举 | frequent→高频，advanced→进阶，common→常见，unclassified→待分类 |
| `q.author` | `author_name` | 用公开展示名称填入卡片 |
| `i.date` | `interview_date` | YYYY-MM-DD转换成页面的YYYY.MM.DD |
| `i.count` | `question_count` | 面经卡片题目数 |
| `i.status`中文文本 | `status`英文枚举 | 按面经状态映射中文，不能套用AI任务的状态字典 |
| `initial`、`color` | 无对应字段 | 前端从公司名取首字并按确定规则选颜色；不必另查接口 |

直接把响应数组赋给`resumeList`或`questionList`，会导致文件类型、日期、分类、作者和选中标记不正确。尤其公开题库的现有筛选使用中文`q.type`，无法直接筛选英文`category`。

还有一个确定的空状态问题：`activeResume`计算属性会回退取列表第一项，即使服务端明确返回`active_resume=null`。简历列表为空时，模板又直接读取`activeResume.name`。

**建议：** 明确选择“页面统一使用接口字段”或“统一适配层转换”其中一种，不要混用。将服务端`active_resume`设为唯一生效来源；返回null时展示上传提示，并禁用生成动作。用户资料及固定统计也要改为绑定响应，不能保留当前硬编码姓名和数字。

### R3 · P1 · 异步接口合理，但当前页面没有可执行的完成流程

**类型：前端接入阻塞，不是缺少更多接口。**

证据：`src/main.js:12`的`ask`立即填入固定答案；第16行仅在`answer`有值时显示面板；第17行题单文件没有绑定处理函数，只有第一步界面，没有进度和结果下载入口；第20行设置输入没有绑定提交数据。第19行“补充问题”按钮也未绑定。

API创建回答返回202且正文为null，直接套用原页面时不会显示“生成中”。批量任务即使创建成功，也没有界面承接后续状态和下载。

**建议流程：**

1. 点击提问后立即展示答案区域的加载状态，并限制重复点击。
2. POST创建任务，保存返回的`answer.id`；不要等待`content`非空才显示面板。
3. 按任务编号轮询；成功展示正文与建议，失败展示错误，并允许用户重试。
4. 批量页上传后保存`job.id`，查询进度；`download_ready=true`才展示可点击下载按钮。
5. 设置页先绑定表单，城市文本拆分成数组后提交；补充问题按钮先有题目输入和确认提交界面。

异步创建与查询拆分是必要的长任务交互，不属于不合理的“同一页一次调用多个接口”。

### R4 · P2 · AI弹窗跳转和异步结果归属缺少规则

**类型：确定的当前页面行为加上异步接入风险。**

证据：`src/main.js:12`的`openAnswer`先调用`ask`，而`ask`立即把页面切换到AI咨询，随后才打开弹窗；但弹窗底部又有“进入AI咨询”。这意味着点击题库“查看回答”时，底层页面已经提前跳转，与底部按钮的含义不一致。

此外，页面所有入口共用`question`和`answer`，没有保存当前显示的`answer_id`。接入真实异步请求后，如果先问A再问B，A的请求更晚完成，可能把B的答案面板覆盖成A的回答；点“清空”后仍在进行的轮询也可能把内容重新填回来。

**建议：** 弹窗打开时保留来源页，仅点击“进入AI咨询”时跳转。显示层保存当前任务编号；只接受与当前显示任务一致的查询结果。关闭弹窗、清空、切换问题或离开页面时停止对应查询，后台任务可继续完成，不必新增取消接口。明确返回来源页时是否保留筛选条件和滚动位置。

### R5 · P2 · 接口分页，但页面没有继续加载入口

**类型：页面与接口交互不完整。**

证据：简历、题库、面经列表接口默认20条并返回`next_cursor`；`src/main.js:15`、第18行、第19行只有遍历列表，没有页码、加载更多或滚动加载。

**影响：** 数据超过20条后，用户只能看到第一页。轮询简历解析状态时如果用第一页覆盖已经加载的列表，还会让后续页记录消失。

**建议：** 为三个列表增加加载更多或滚动加载，首次请求清空游标，后续追加并按ID去重；筛选变化时重置列表。解析轮询只合并状态更新，不覆盖已加载的其他页面。无需为了适配原型而一次返回无限数量数据。

### R6 · P2 · 请求约束只写在说明中，OpenAPI不能表达真实要求

**类型：确定的契约缺失。**

证据：`scripts/export-openapi.mjs:62`仅生成普通对象Schema；最终AI创建请求没有`oneOf`，设置PATCH没有`minProperties`，字符串长度等限制也未落入Schema。

| 接口场景 | 现有问题 | 应明确的规则 |
| --- | --- | --- |
| AI创建回答 | 两个字段都非必填；`{}`和同时提交两个字段均不被Schema排除 | 使用oneOf表达二选一，各分支要求对应字段 |
| 保存设置 | 所有字段可选，空对象也符合当前Schema | 至少一个字段；限制未知字段后，空对象不能作为有效修改 |
| 保存或追加题目 | 追加题目没有结构化minItems；题干长度只写文字 | 至少1题、单次不超过200题；每项1～4000字；追加后总数校验由服务端读取现有记录完成 |
| 公司、姓名、关键词 | 长度只在注释中 | 对应minLength/maxLength；纯空格仍须服务端trim后校验 |
| 日期 | 只有string | format=date，约定用户时区默认值 |
| 所有请求对象 | 总约定说不允许未知字段，Schema却未设置 | 对请求对象设置additionalProperties=false；响应是否允许扩展另行约定 |
| 默认分页与模板格式 | 默认值只写描述 | 同步default=20、default=xlsx等可表达默认值 |

路径参数`question_id`的通用注释还写着“可为null”，但浏览接口路径中的题目编号必须非空；切换接口的`resume_version_id`注释也误用了“回答依据版本”的用途。字段说明需要按请求、路径、响应的具体位置编写，不能仅按字段名称套用一段话。

### R7 · P2 · 同一接口的请求与返回示例存在业务矛盾

**类型：确定的文档示例错误。**

证据：`docs/api-design.md:1509`“保存面试记录及全部问题”，请求明确传入`role=后端开发工程师`，对应成功响应却返回`role=待补充职位`。这不是跨接口不同时间点造成的差异，而是同一次保存示例内部不一致。

**影响：** 前端无法判断岗位是否可传、后端是否忽略该参数，生成的Mock结果也不适合验证表单保存。

**建议：** 与当前页面严格对应的请求示例省略页面没有的role与interview_date，由后端填默认值；如果保留可选扩展参数的示例，则响应必须回显实际传入的岗位。增加请求示例与返回业务字段的一致性检查，不能只验证类型。

### R8 · P2 · 各HTTP错误都返回“简历未就绪”的示例

**类型：确定的文档导出错误。**

证据：`scripts/export-openapi.mjs:70`给所有接口的400、401、403、404、409、413、415、422、429、503复用同一个`RESUME_NOT_READY`错误示例。

**影响：** 未登录、文件超限、资源不存在等场景的业务码与提示完全不对应。前端无法按文档正确实现登录失效提示、上传校验和失败重试；模板等接口也出现了与业务无关的简历错误。

**建议：** 按HTTP状态和实际场景定义错误码，如401使用UNAUTHENTICATED，413使用FILE_TOO_LARGE，422在AI接口中使用RESUME_NOT_READY。每个接口列出实际可能出现的错误，不机械附加所有错误。下载接口同样约定失败时返回JSON错误、成功时返回文件流，并在OpenAPI响应头中声明Content-Disposition。

### R9 · P2 · 自动分类与跨页面数据更新未形成完整闭环

**类型：接入流程缺失。**

证据：`docs/api-design.md:1509`保存面经返回`classification_status=pending`，设计流程只写保存后刷新当前页。后台完成分类后不会自动修改已经显示的页面；`src/main.js:12`当前的本地保存则会同时更新面经列表和公开题目数组。全局“记录面试”弹窗在任何页面都能打开。

**影响：** 自动分类后的题目可能一直显示“待分类”；技术题占比不更新。用户在一个页面保存或切换简历，再切换到使用旧缓存的另一页面时，也可能继续看到旧列表、旧统计或旧简历。

**建议：**

1. 保存后记录受影响的面经ID，详情中有pending题目时有限轮询已有详情接口；全部为succeeded或failed即停止，不新增逐题查询接口。
2. 后台识别后同时使公开题库、首页推荐和面经统计缓存失效。
3. 前端对首页、面经列表、详情、公开题库做失效标记，切换到相关页面时重新获取聚合数据。
4. 简历切换成功后同步共享的active_resume状态；旧回答仍标明其实际使用版本，不能把旧答案标成基于新简历。
5. 请求重试复用原幂等键；用户主动创建新一次回答才使用新键，避免网络重试重复生成。

| 页面/入口 | 数据与接口覆盖 | 判断及前提 |
| --- | --- | --- |
| 首页 | 用户、生效简历、简历卡片、公开题目均有返回 | 聚合合理；需要R1、R2修正；最多3条是建议展示策略，当前页面会遍历所有本地数据 |
| 我的简历 | 列表、上传、切换、解析状态均覆盖 | 不缺核心接口；需要空状态、完整解析状态展示及分页 |

| 回答弹窗 | 可复用AI创建与查询 | 页面跳转时机需要按R4统一，不能打开弹窗即提前跳走 |

| 记录面试弹窗 | 公司、城市、薪资、分类模式、题干数组、公开开关覆盖 | 与页面一致；Excel本地提取题干后提交数组，无需再上传同一文件 |

| 通知、卡片省略号 | 没有具体业务行为 | 暂不凭图标添加查询、删除或编辑接口，需要先有明确交互需求 |

## 三、建议的接入顺序与调用链

### 1. 先接通同步页面

打开首页→GET首页聚合→保存当前用户与active_resume→展示简历及公开题目。进入题库或面经列表时，各调用对应聚合接口；无需为每张卡片再查询公司、作者或题数。

建立统一请求层，处理认证、业务错误、字段转换、加载状态和请求过期结果。列表页面再补分页；不要先把原型数组直接替换成未经适配的响应对象。

### 2. 简历上传与生效

选择文件→POST上传→按返回卡片显示等待解析并同步激活状态→查询简历管理聚合→解析成功后启用AI提问。

点击其他简历→PUT切换→以服务端成功响应为准更新生效状态。切换失败时保留原选中项；不能像原型一样无条件先提示“已切换”。

### 3. AI咨询与弹窗

确认简历已就绪→自由提问传question_text，题库/面经提问传question_id→POST创建→记录任务ID→GET查询→成功展示答案或失败展示原因。

提问页和弹窗可以共用请求逻辑，但不能共用一个没有任务归属判断的临时答案字符串。主动重复询问和网络重试需要区分幂等键。

### 4. 保存面经与自动分类

手填或本地Excel解析→一次POST保存面经及全部题目→成功后关闭弹窗、使相关页面缓存失效→按需进入详情→有待分类题目时有限轮询详情→分类结束更新题目标签及统计。

保存失败应保留用户填写内容；只有成功后才重置表单。原型中的默认公开=true可保留，但应与请求的is_public一致。

### 5. 批量答题

GET批量页→检查简历与限制→POST上传创建任务→GET进度→download_ready=true→GET下载结果。

正常流程只有一个任务查询，不逐题发请求。结果为partial_failed时仍展示下载入口。重复进入页面用latest_job恢复最近任务，同时显示该任务实际引用的简历，避免与当前生效简历混淆。

### 6. 设置

GET设置页→绑定表单→城市文本转数组、偏好文本转枚举→PATCH保存→用完整返回值更新表单和共享用户资料。

## 四、需要确认的业务决定

以下不能仅凭页面确定，不作为已经发现的实现错误：

- **“查看回答”的含义：** 当前代码每次生成个人答案，现有契约遵循这一行为。如果业务希望查看发布者预先分享的标准答案，就需要单独的公开答案读取设计；不能把私人简历答案直接公开。
- **“难度”的定义：** 弹窗文案说AI识别分类和难度，卡片却使用高频、进阶、常见等混合标签。需要确认继续保留展示标签，还是分别定义难度与出现频率。
- **浏览与帮助人数口径：** 页面仅展示数字，按人按天去重和按作者去重是建议口径，尚无后端事实证明。若保留独立浏览接口，应只在公开题目实际打开时调用，不与服务端生成回答时的计数重复执行；浏览计数失败不阻塞回答。
- **限制与默认值：** 200题上限、首页3条摘要、用户时区缺省日期均为建议；页面当前未明确这些限制，需要同步提示。岗位与日期在弹窗没有输入项，不应要求前端凭空提供。

## 五、合理之处与不必新增的接口

- 首页、面经列表与详情聚合返回符合页面展示结构，不需要拆出统计、公司、作者等逐项接口。
- 保存面经和所有题目作为一次事务提交，可以避免半场记录保存成功、题目只保存一部分。
- 简历解析与AI生成放到后台合理，不能为了“页面一次请求”让首屏等待全部AI操作结束。
- 任务固定简历版本合理，能够解释“这条答案是依据哪份简历生成的”。
- 公开题库直接从公开面经的题目读取，避免维护第二份题目数据导致不同步。
- 记录面试的Excel现有逻辑在浏览器提取题目，提交题干数组即可；批量答题为保留原表及生成文件，上传原始文件也合理，两者用途不同。
- 通知、删除简历、修改面经状态等操作没有已实现页面行为，不应仅凭展示字段推导出额外接口。
